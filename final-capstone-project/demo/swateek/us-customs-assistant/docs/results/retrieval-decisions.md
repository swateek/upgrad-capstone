# Retrieval decisions (plan step 9, §6)

Decided on the **dev** labels (17 questions, 45 citation claims); the **frozen** labels (69 questions, 220 claims) are reported next to them and were not used to choose. Full tables: `retrieval_experiment.md` (generated by `backend/eval/retrieval.py`). Upgrad calls used: 44 embedding requests for the query vectors and 45 listwise chat calls on dev (`docs/quota-log.md`).

**How it is scored.** The unit is one (question, gold citation claim) pair. A claim is found when a retrieved chunk holds one of its acceptable clause ids, which come from the independent gold. Every chunker is therefore scored the same way.

Recall at a fixed k favours big chunks: five whole sections are about 3,600 tokens, five 200-token windows about 900. So the deciding metric is **R@1.5k**: the claim is found within the first 1,500 tokens of passages. That is about what one writer call can take under the plan's ~3k input-token target (§4.6). R@1/3/5/10 are reported as well.

**Configuration shipped** (`config.py`, `env.sample`):

| Setting | Value |
|---|---|
| Chunks | `window200` |
| Retrieval | hybrid: BM25 + bge dense, RRF k=60 over the top 20 of each |
| bge query prefix | on |
| Query | built by code: the question + the rule names (`customs/retrieval/query.py`) |
| Topic filter | on |
| Reranker | none |
| Passages per search | up to 1,500 tokens, best first |

## What mattered most: the query, then the topic filter

These two levers are not among the three decisions. They are set by design (plan §4.4), and the experiment measured them.

| window200, hybrid, prefix on | dev R@5 | dev R@1.5k | frozen R@5 | frozen R@1.5k |
|---|---|---|---|---|
| Question only (what `single_rag` sends) | 0.22 | 0.36 | 0.25 | 0.32 |
| Question + rule name | 0.49 | 0.60 | 0.51 | 0.54 |
| Question + rule name + topic filter | **0.67** | **0.84** | **0.69** | **0.77** |

A traveller's question names wine, Paris and $90, not "flat rate duty" or "excise general rates". The rule names come from the calculators' `rule_refs`, so code adds them and no model writes queries (small-model log #27, #30). The topic filter keeps the sanctions and rate tables, which make up about 70% of the chunks, out of exemption searches. Hard negatives in the top 5 stay at or below 0.06.

## Decision 1: chunking → `window200`

| hybrid, prefix on, qr + topic | tok@5 | dev R@5 | dev R@1.5k | frozen R@5 | frozen R@1.5k |
|---|---|---|---|---|---|
| paragraph (with header) | 1,568 | 0.73 | 0.67 | 0.67 | 0.63 |
| section (whole) | 3,631 | **0.82** | 0.27 | **0.74** | 0.31 |
| window200 | **917** | 0.67 | **0.84** | 0.69 | **0.77** |

Whole sections win recall@5, but only by spending four times the tokens. Within the writer's budget they drop to 0.27, because one or two long sections fill the budget (§148.33 alone is 920 tokens; HTSUS General Note 3 is 2,612). 200-token windows give the best recall per token. Frozen agrees with dev on the ordering.

Trade-off accepted: a window can cut a clause in two. The chunk carries every clause id it overlaps, and citations still resolve by clause id (D20).

## Decision 2: embedding → bge query prefix **on**

| window200, qr + topic | dev R@5 | dev R@1.5k | frozen R@5 | frozen R@1.5k |
|---|---|---|---|---|
| hybrid, prefix on | **0.67** | **0.84** | 0.69 | 0.77 |
| hybrid, prefix off | 0.58 | 0.80 | 0.69 | 0.77 |
| dense only, prefix on | 0.64 | 0.69 | 0.59 | 0.71 |
| dense only, prefix off | 0.60 | 0.64 | 0.59 | 0.75 |

On dev, the prefix gives +0.09 at R@5 and +0.04 at R@1.5k. Frozen shows a tie, so the effect is small. Prefix on is bge's documented use for retrieval queries, so we keep it on. Hybrid beats either retriever alone: BM25 alone reaches 0.69 at R@1.5k on dev, dense alone 0.69, hybrid 0.84. BM25 catches exact terms ("9816.00.20", "proof gallon") and dense catches paraphrase.

## Decision 3: reranker → **none**

| window200, hybrid, prefix on, qr + topic | R@1 | R@3 | R@5 | R@10 | R@1.5k | cost per search |
|---|---|---|---|---|---|---|
| none | 0.22 | 0.49 | 0.67 | 0.84 | **0.84** | 0 calls |
| local cross-encoder (ms-marco-MiniLM-L-6-v2) | 0.16 | 0.51 | 0.64 | 0.78 | 0.71 | 0 calls; local CPU |
| Qwen3-8B listwise (top 20 → 10) | **0.29** | **0.62** | **0.73** | **0.89** | 0.82 | 1 chat call, ~4,000 tokens |

All figures are dev, 45 claims.

- **Cross-encoder: rejected.** It is worse than no reranker on every metric on dev, and on frozen R@5 too (0.55 vs 0.69). It wrecks rule-specific claims: on frozen, the allocation rule (R11) falls from 1.00 to 0.11 and the Cuba rule (R4) from 1.00 to 0.62. It was trained on web search (MS MARCO), not regulatory text. It also reads only the first 512 tokens, which hurts it most on whole sections (frozen R@5 0.74 → 0.47).
- **Listwise: better ordering, not worth the cost.** It improves the top of the list (R@1 +0.07, R@3 +0.13). Within the 1,500-token budget the writer actually gets, it is no better (0.82 vs 0.84). Each search would cost one more model call and about 4,000 tokens. That is a third of the 12,000-token per-question budget, and one of the 10 model calls, on an endpoint that serves one request at a time. All 45 replies parsed; there were no fallbacks.
- Listwise stays implemented and switchable (`RERANKER=listwise`), and it counts toward the caps if turned on. It was not run on frozen (`COMPENSATIONS.md` #8).

## What retrieval still misses, and what covers it

R@1.5k on frozen, by rule, for the shipped configuration (from `retrieval_experiment.md`):
- **Low:**
  - R9 "which exemption": 0.50 over 62 claims;
  - R3 under-21: 0.50 over 4;
  - R12 brand ≠ origin: 0.00 over 1;
  - the Florida flag: 0.00 over 2.
- **High:**
  - R1, R2, R4, R5, R11 and four of the five states: 0.94–1.00;
  - R7: 0.93;
  - R8: 0.78.

R9 is the big one. The question rarely says "exemption", and the acceptable clauses are spread across §148.35, §148.36 and HTSUS 9804.

This is why citations don't depend on retrieval alone (D20). Each calculator result carries rule ids that map to signed-off clause ids. When a rule's clause is not among the retrieved passages, the executor fetches it by id and logs `retrieval_miss_recovered`. The end-to-end runs report that rate next to recall@k, so this table and those runs together show how much the fallback carries.
